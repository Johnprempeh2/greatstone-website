# Client Deep Dive documents (GRE-2620)

The signed-in client opens `#portal/deep-dive`. `POST /api/deep-dive-document?requestId=<uuid>` accepts one file per open request. The request body is the raw file. The browser sends its UTF-8 display name as base64url in `x-file-name-encoded`; the bridge can also send an ASCII `x-file-name`. The server verifies the Supabase session, resolves the linked GSAM tenant through `asCustomer`, checks that the request is open in the current snapshot, validates the bytes and extension, and stores them in the private `deep-dive-client-documents` Netlify Blob store. The size limit is 25 MB. Supported formats are PDF, XLSX, XLS, CSV, TXT, PNG, JPEG, GIF, WebP, SAV and ZSAV.

The client sends the response through `/api/deep-dive-client`. The pending answer references the uploaded document. The signed callback to GSAM includes `fileName`; only a confirmed callback changes the answer to `received`. A failed callback keeps the answer and document for retry. GSAM retrieves the uploaded bytes with a signed **read** bridge call to `GET /api/deep-dive-document?bridge=1&tenantId=<uuid>&requestId=<uuid>`. The response is an attachment. This route uses the existing GSAM bridge v1 signature, nonce and audit transaction. A retry uses the same request ID.

GSAM releases collected documents and deliverable files to the site with a signed **write** bridge call to `PUT /api/deep-dive-document?tenantId=<uuid>&sourceId=<uuid>&kind=collected|deliverable`. The body is raw bytes, `x-file-name` is required, and the call uses the existing v2 idempotency key, signature and audit transaction. The source ID must be a held file or published/accepted deliverable in the current tenant snapshot. The site stores one immutable file per source ID and kind. Replacing a release requires a new source ID. Clients list and download collected documents through authenticated `GET /api/deep-dive-document`. Deliverable files in this store are not client-readable.

For a client deliverable, staff or an authorised portal agent creates a `deep_dive` draft in `portal_documents`, enters the released content and attaches a designed PDF through the existing portal file path. Staff submits it for approval. The registered approver reviews its database fingerprint and publishes that exact version. Only then does it appear in the client portal and under Published deliverables on `#portal/deep-dive`. The client reads it at `#portal/doc/<id>` and accepts it through `portal_accept`; the append-only acceptance, audit and receipt job use the same path as every other portal document. A replacement is a new version in the same series. The Deep Dive snapshot's deliverable title or bridge upload alone does not publish a portal document.

Migration `061_deep_dive_portal_documents` only extends the document kind constraint. It preserves all existing portal policies, approval triggers and receipt jobs. Its rollback refuses to run while any `deep_dive` document version exists; archive and retain the related approvals, acceptances and receipts before planning a new forward migration to remove the kind. The legacy Supabase mirror is `0041_deep_dive_portal_documents.sql`.

Migration `058_deep_dive_documents` creates the tenant-scoped file index with forced RLS, a guard against attaching another request's file to an answer, and narrow client and bridge grants. The migration is additive. To roll back in a test environment, first preserve any uploaded files and pending answers, then apply `058_deep_dive_documents/rollback.sql`. Do not run the rollback on a live database while either exists. Old blob objects are not deleted by SQL; retention and deletion are an operational follow-up.
